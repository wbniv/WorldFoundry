- [ ] **Bug: texture UV repeat broken for mesh UVs outside [0, ~5].** GL_REPEAT is set on textures at [`pixelmap.cc:208`](wfsource/source/gfx/pixelmap.cc), and the modern GL backend's fragment shader at [`backend_modern.cc:114`](wfsource/source/gfx/glpipeline/backend_modern.cc) just calls `texture(u_tex, v_uv)` (so REPEAT should kick in natively). ## CONCURRENCY / ASYNC

The 1994 cooperative tasker (`hal/tasker.cc`) was never completed for Linux (context-switch
asm was never written) and is being deleted.  If a use case arises (background loading,
timer callbacks, concurrent AI), explore these alternatives instead:

- [ ] `std::thread` + work queue — simplest; good for background asset loading
- [ ] C++20 coroutines — stackless; fits scripted AI / state-machine actors well
- [ ] Fiber library (e.g. Boost.Context or `libco`) — stackful cooperative tasks, closest to the original tasker model; worth revisiting if multiple concurrent game tasks are needed

- [ ] **IFF chunk names aren't a first-class FOURCC type (audit + cleanup).** A [FourCC](https://en.wikipedia.org/wiki/FourCC) ("four-character code") is the 4-byte tag the IFF spec uses to name every chunk, but our IFF layer only models it half-way: [`IFFTAG(a,b,c,d)`](wfsource/source/iff/iffread.hp) (`iffread.hp:48`) expands to a **bare `uint32`**, while the [`ChunkID`](wfsource/source/iff/iffread.hp) wrapper (`iffread.hp:69`, holds an `int32`) exists but `IFFTAG` never produces one — so every dispatch reads `case IFFTAG('B','M','P','L'):` and has to *unwrap* the typed `ChunkID` back to a raw int via `GetChunkID().ID()` to match the untyped literal. - [ ] **Consider 8-byte alignment in the IFF file format itself.** Today IFF chunks are 4-byte aligned (`int32 _alignedChunkSize = (_chunkSize + 3) & ~3;` at [`iff/iffread.cc`](wfsource/source/iff/iffread.cc):55, matching the chunk-size field's own 32-bit width). That was correct for the PS1 32-bit-pointer era when these files were authored; on 64-bit hosts it means every chunk whose payload contains a pointer / `int64_t` / `double` ends up on a 4-aligned-but-not-8-aligned offset, requiring either an aligned scratch buffer + memcpy on read, or unaligned-access tolerance from the consumer (the latter is what the engine relies on today and what ASan/UBSan correctly complains about for the few exceptions). Bumping in-file chunk alignment to 8 bytes would (a) let consumers read structured payloads as native types without copy, (b) save the `memcpy` cost on hot paths like asset map / animation channel loading, (c) align with how everyone else has written file formats since ~2003. The IFF spec (1985, Electronic Arts) explicitly allows even/word alignment for chunks; 8-byte is fine inside the spec and is how modern descendants like RIFF/WAVE handle 64-bit payloads.
