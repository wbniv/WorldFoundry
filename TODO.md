- [ ] **IFF chunk names aren't a first-class FOURCC type (audit + cleanup).** A [FourCC](https://en.wikipedia.org/wiki/FourCC) ("four-character code") is the 4-byte tag the IFF spec uses to name every chunk, but our IFF layer only models it half-way: [`IFFTAG(a,b,c,d)`](wfsource/source/iff/iffread.hp) (`iffread.hp:48`) expands to a **bare `uint32`**, while the [`ChunkID`](wfsource/source/iff/iffread.hp) wrapper (`iffread.hp:69`, holds an `int32`) exists but `IFFTAG` never produces one — so every dispatch reads `case IFFTAG('B','M','P','L'):` and has to *unwrap* the typed `ChunkID` back to a raw int via `GetChunkID().ID()` to match the untyped literal. Knock-on effect: because neither the tag nor the chunk's on-disk record is a real type, per-site code hand-encodes element widths as `sizeof(int32)`/`sizeof(packedAssetID)` (e.g. [`rendcrow.cc`](wfsource/source/renderassets/rendcrow.cc) `_nTextures = chunkSize / sizeof(...)`) — exactly the LP64 `long`-width trap the [long audit](docs/plans/2026-05-20-runtime-long-audit.md) just chased. Fix: make `FourCC` a real 4-byte type, have `IFFTAG`/`ChunkID` *yield* it, `switch` on it directly (drop the `.ID()` unwrap), and model fixed-width chunk records so the 4-byte word size is intrinsic to the format instead of re-asserted at each call site — at which point you don't encode an element type at all. Surfaced 2026-05-20 reviewing the long-audit `rendcrow` fix.

- [x] **HAL pool allocators round size to 4 bytes — should be 8 on 64-bit hosts.** DONE 2026-05-19 commit `f10cec5`; refined to compile-time `WF_POINTER_ALIGN` (= `sizeof(void*)` with 32-bit-ARM-AAPCS carve-out) in commit `292af66` — ESP32-ready, byte-identical codegen on 64-bit hosts. Root cause: [`lmalloc.cc:223`](wfsource/source/memory/lmalloc.cc) and [`dmalloc.cc:174`](wfsource/source/memory/dmalloc.cc) both have `size += (4-(size&0x3))&3;` — round up to 4-byte boundaries. Correct for the PS1 32-bit-pointer convention these allocators date from; one bit short on x86_64 where `void*`, `int64_t`, `std::atomic<T*>`, `double` all want 8-byte alignment. **Fix:** change `0x3` → `0x7` and `4-` → `8-` in both lines, plus ensure each pool's base `_memory` pointer is 8-byte aligned at construction (the LMalloc/DMalloc ctors get a raw `char* mem` from the parent pool; round at construction or assert on caller side). Benign on x86 (1-cycle penalty per misaligned load), real bug on strict-alignment ARM/iOS — fix before iOS Phases 4–5 ship. Tracked separately from [BUGS.md](docs/BUGS.md)'s "BaseObjectIterator missing virtual destructor" entry (same ASan run that caught both).
- [ ] **Consider 8-byte alignment in the IFF file format itself.** Today IFF chunks are 4-byte aligned (`int32 _alignedChunkSize = (_chunkSize + 3) & ~3;` at [`iff/iffread.cc`](wfsource/source/iff/iffread.cc):55, matching the chunk-size field's own 32-bit width). That was correct for the PS1 32-bit-pointer era when these files were authored; on 64-bit hosts it means every chunk whose payload contains a pointer / `int64_t` / `double` ends up on a 4-aligned-but-not-8-aligned offset, requiring either an aligned scratch buffer + memcpy on read, or unaligned-access tolerance from the consumer (the latter is what the engine relies on today and what ASan/UBSan correctly complains about for the few exceptions). Bumping in-file chunk alignment to 8 bytes would (a) let consumers read structured payloads as native types without copy, (b) save the `memcpy` cost on hot paths like asset map / animation channel loading, (c) align with how everyone else has written file formats since ~2003. Tradeoffs: every existing `cd*.iff` plus standalone-level `.iff` outputs would need to be re-emitted (cheap — the Rust iffcomp-rs handles every format we ship), and `iffcomp` / `levcomp` Rust tools need a one-line padding bump (`(size + 3) & ~3` → `(size + 7) & ~7`). The bigger lift is auditing every reader site to confirm they handle the new padding correctly (most use `IFFChunkIter::Next` which already skips padding; the corner cases are the few hand-rolled offset reads like the now-fixed `level.cc:1394`). **Worth doing** alongside any future asset-pipeline bump, low priority by itself. The IFF spec (1985, Electronic Arts) explicitly allows even/word alignment for chunks; 8-byte is fine inside the spec and is how modern descendants like RIFF/WAVE handle 64-bit payloads.
