### Monitor

- **zForth dictionary size** — append-only dict grows with every unique script word + all `INDEXOF_*` constants; fixed at `ZF_DICT_SIZE` (64 KB in `zfconf.h`, ~100 reloads). If level script count grows: bump `ZF_DICT_SIZE` or reinit `g_ctx` at level unload + replay bootstrap. [investigation](docs/investigations/2026-04-29-forth-compile-run-audit.md)
- **Never write `new (pool) T[n]` for a pool-allocated array** — use `MEMORY_NEW_ARRAY`/`MEMORY_DELETE_ARRAY` (`memory/memory.hp`) or the raw-allocate-then-placement-construct pattern in `Array<T>::SetMax`. The compiler's hidden array cookie is 8 bytes under the generic Itanium ABI (x86_64) and **16** under the ARM C++ ABI (every arm64 target: Apple, Android, aarch64 Linux), so any code doing pointer arithmetic over it is right on one platform and silently corrupts the heap on the other — that is what blocked the first macOS run. Guarded on every host by `wf_game --memory-test` (ctest `memory_pool_arrays`, `memory/pooltest.cc`), but the guard only covers the helper, not a fresh call site. The remaining `new (pool) T[n]` sites (`gfx/rendobj3.cc`, `anim/anim.cc`, `iff/disktoc.cc`, `cpplib/int16li.hpi`) are safe **today** only because those element types are trivially destructible and so carry no cookie at all — adding a destructor to any of them reintroduces the bug. [plan](docs/plans/2026-09-20-macos-phase0-green-baseline.md)
- **Never link `libwfcrdt.a` into `libwfengine.a`** — engine stays Rust-free (editor owns the Y.Doc). If a change appears to "simplify" by linking it in: STOP and re-open the design decision (would bloat every iOS/Android/`wf_game` binary with dead Rust, chain mobile CI to the Rust toolchain, couple engine ABI to Yrs churn). [plan](docs/plans/2026-05-18-yrs-c-abi-binding.md)
