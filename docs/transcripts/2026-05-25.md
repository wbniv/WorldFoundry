## Summary Report: Is a Compiled Binary Level "Self-Describing"?

Based on my investigation of the WorldFoundry codebase, the phrase **"a binary level isn't self-describing"** is **literally accurate but technically imprecise**. Here's the detailed breakdown:

### 1. Binary `.lvl` Layout — Positional, Not Self-Describing

The `.lvl` (or `LVL` chunk in `cd.iff`) is **purely positional binary**, containing:

**File structure** (`wftools/levcomp-rs/src/lvl_writer.rs:1-17`):
```
_LevelOnDisk header            52 bytes
int32 objectsOffsets[N]        4·N bytes  (offsets only, no names)
_ObjectOnDisk + OAD data       variable per object, 4-byte aligned
```

**Per-object structure** (`lvl_writer.rs:32-42`):
```
type (i16)           at byte 0
padding              2 bytes
position (i32×3)     bytes 4–16
scale (i32×3)        bytes 16–28
rotation (u16×3)     bytes 28–36
bbox (i32×6)         bytes 36–60
oadFlags (i32)       byte 60
pathIndex (i16)      bytes 64–66
OADSize (i16)        bytes 66–68
[OAD data payload]   variable
```

**Critical fact:** The binary contains **NO field names, NO labels, NO enum option lists**. Field **values are packed positionally** in the order defined by the schema. The byte offsets within the OAD payload are **not encoded in the binary** — they're determined entirely by the schema definition.

**Evidence:** `oad_loader.rs:65-91` shows that field size is computed per `ButtonType` (Int32 = 4 bytes, Fixed16 = 2 bytes, String = configured length, etc.). The serializer (`lvl_writer.rs:148-162`) calls `serialize_oad_data` which walks the schema in order and packs values at the offsets the schema defines. Reading would require doing the exact same walk.

### 2. Schema Files and Their Roles

The three **distinct** schema layers work together:

| File | Purpose | Built From | Used By |
|------|---------|-----------|---------|
| **`.oas`** (e.g., `player.oas`) | **Master source**: per-class field definitions. Text macro language with `TYPEHEADER` / `TYPEENTRY` / `@include` directives | Handwritten by developers | `oas2oad-rs` compiler |
| **`.oad`** (e.g., `player.oad`) | **Compiled binary schema**: ordered list of `OadEntry {name, ButtonType, showAs, Min, Max, enum_options, …}`. Fully resolved (all `@include` chains flattened). | Generated by `oas2oad-rs` from `.oas` + `objects.lc` | Editor, `wfmut` bridge, levcomp-rs |
| **`.ht`** (e.g., `player.ht`, `common.ht`) | **C struct layout**: defines the in-memory binary layout as a C struct with sized fields. Accessor methods for fixed-point. **This is the ground truth for byte offsets.** | Generated by `regen-headers.sh` via `cstruct` from the schema | Engine code that `memcpy`s the binary directly into these structs at runtime |
| **`objects.mac`** | **Master actor-kind enumeration**: lists every instantiable actor class by name with a collidability flag. Determines the `EActorKind` enum in `objects.h`. | Handwritten; defines canonical `OBJECTENTRY(ClassName, collidable)` list | `oas2oad-rs` uses it to resolve `MovementClass` defaults; engine dispatch table |
| **`objects.h`** | **Generated enum**: `enum EActorKind { NULL_KIND, ActBox_KIND, Player_KIND, … }` — one entry per `OBJECTENTRY` in `objects.mac` | Generated from `objects.mac` | Engine actor factory dispatch |

**Critical relationship:** The `.oad` file is the **authoritative field layout definition**. When the engine loads a binary actor, it:
1. Reads the object header (type, position, bbox, OADSize)
2. Looks up the class's `.oad` schema 
3. Walks the `.oad` entry list in order
4. For each entry, reads `field_size(entry)` bytes from the binary
5. Stores the value in the corresponding `.ht` struct field

The byte offsets are **implicitly** defined by the schema walk order, not stored in the binary.

### 3. Can the Binary Alone Be Reconstructed to Named Fields?

**No. Without the schema files, the binary cannot be reliably reconstructed.**

**What's present in the binary:**
- Positional field values (packed bytes)
- Actor class ID (index into the `EActorKind` enum)
- Bounding box and position (which are named in the `.ht` struct, not the OAD)

**What's missing:**
- Field **names** (position 68–95 → which field?)
- Field **types** (is it an int, fixed-point, enum, string, object reference?)
- **Enum option lists** (value 11 is "Mesh" for Model Type, but nothing in the binary says that)
- **Min/Max ranges** (scalar clamps)
- **Interpretation hints** (`showAs=MAILBOX`, `showAs=COLOR`, etc.)

**Why reconstruction fails:**
If you have just the `.lvl` binary and no `.oad`, you cannot:
- Say "bytes 68–72 are the Mass field" (without the schema, you don't know)
- Say "value 11 in the Model Type field means 'Mesh'" (without the enum list)
- Reconstruct the named tree the editor shows

However, **if you have the binary PLUS the schema files (OAS/OAD) for every class in it**, you CAN reconstruct the named-field tree completely. The schema defines the field-order contract, and positional reading against the schema recovers all names, types, and labels.

### 4. The Golden-Source Convention

From **`docs/plans/2026-05-20-editor-property-panel.md`**:

&gt; **"Running the editor from a compiled `cd.iff`/level binary — a binary level isn't self-describing (no inline names/labels), so it would need the OAD/IFF C++ reader to interpret *everything*, not just the editor metadata. Out of scope while we source from the text `.lev`/`.iff.txt`."**

And from **`wf-edit-manual.md:127-132`**:

&gt; **"Field names, values, enum labels, and the actor's class all come straight from the self-describing `.lev`; the `.oad` schema supplies the widget type, enum option lists, and min/max ranges."**

**The convention is:**
- The **text `.lev`** (exported from Blender) is the **golden source**. It carries inline `NAME` chunks for every field, making it fully self-describing for viewing in an editor.
- The **compiled binary `.lvl`** is a **derivative** (optimized for runtime load, not authoring). It is **not** meant to be edited; round-tripping a binary → edit → binary would lose the intent of the text source.
- The **editor always sources from `.lev`** text, not from the compiled `cd.iff`, because:
  1. Field names are inline in the `.lev` (no schema lookup needed for a read-only view)
  2. Comments and authoring structure are preserved in text (lost in binary)
  3. The `.lev` is the contract; the binary is an optimization

### 5. The REAL Reason the Editor Loads Text, Not Binary

The phrase "binary levels aren't self-describing" conflates two separate concerns:

1. **Self-description (metadata):** The `.lev` text carries `NAME` sub-chunks for every field, so a pure text-reader doesn't need the schema. The binary does not — it's purely positional.

2. **Practical authoring:** Even if the binary could be reconstructed with the schema, it would be **unwise** to edit the binary or round-trip it back because:
   - Ordering of unrelated fields in the schema may change between versions
   - Comments and structural notes are lost
   - Asset references and relative paths may be ambiguous
   - The `.iff.txt` source-of-truth would be orphaned

**The actual design decision:** Source from the text `.lev` as the lasting record of intent, compile it once to binary for runtime, and treat the binary as an ephemeral cache. This is a **convention choice, not a technical limitation**. The editor *could* load from binary + schema, but it chooses not to because the text source is more durable.

### 6. What Would Be Lost if You Round-Tripped?

If you extracted a binary level, reconstructed it with the schema, edited it, and re-serialized:

- ✅ **Recovered:** All field names, values, enum labels, class types
- ✅ **Preserved:** Field order (per schema) and type information
- ❌ **Lost:** Comments in the `.lev` source
- ❌ **Lost:** Structural grouping/hierarchy (the source `.lev` may have actors organized hierarchically; the binary flattens them)
- ❌ **Lost:** Symbolic asset references (if a Mesh Name changes from relative to absolute path, the binary may not track the intent)
- ❌ **Lost:** Ordering information (if the schema reorders fields, the binary's positional layout doesn't reflect the original `.lev` order)

**The phrase "a binary level isn't self-describing" is literally accurate** — the binary has no inline field names or metadata. However, it is **technically incomplete**. A more precise statement:

&gt; **"A compiled binary level is positionally-defined and schema-dependent. It can be reconstructed to named fields with the corresponding OAS/OAD schema files, but the design convention treats it as a runtime-only optimization, not an authoring source. The text `.lev` is the golden source because it is self-describing and preserves authoring intent."**
