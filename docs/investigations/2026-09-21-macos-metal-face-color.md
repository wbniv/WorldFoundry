# Single-face color mismatch between macOS Metal and Linux OpenGL

**Date:** 2026-09-21

**Status:** Resolved and verified on both platforms.

**Branch:** `fix/macos-metal-face-color` (isolated worktree `/tmp/wf-metal-face`).

**Related plan:** [macOS Metal renderer, §8](../plans/2026-09-20-macos-metal-renderer.md#8-verification).

The two renderers received different vertex colors for the same procedural cube. The cause was the old `MakeRandMaterialList` implementation: it depended on both libc's random-number algorithm and the compiler's evaluation order for constructor arguments. Both renderers correctly shaded their respective inputs. A portable color sequence with explicit channel order fixes all 455 affected pixels while preserving the Linux reference capture exactly.

[![Linux reference, Metal before, Metal after, with enlarged face crops](../plans/2026-09-20-macos-metal-renderer/face-comparison.png)](../plans/2026-09-20-macos-metal-renderer/face-comparison.html)

## Symptom and established baseline

At backend frame 20 of snowgoons, with a deterministic `-rate20` clock, one cube face was flat pink `(191,71,128)` on Linux and flat teal `(43,84,98)` on macOS. The 455 substantially different pixels occupied the inclusive screen rectangle `(313,389)`–`(330,422)` in a 640×480 capture.

Earlier investigation had already excluded timing/frame offset, a different object, and geometry/transform differences. Both platforms submitted 1,563 triangles per frame; the cube silhouette and black faces agreed. No texture-creation failures were logged. These established results were retained rather than repeating that investigation.

The starting hypothesis was texture selection: World Foundry treats white vertex colors as textured and other colors as flat. Both fragment shaders implement that convention. A solid texture could therefore explain a flat face, but a shader change would have been premature without comparing inputs.

Two reproduction details mattered:

- The previous scratchpad's `linux-frame20.png` was an older unmatched capture. `det1.png`, `linux-seam20.png`, and `lx20.png` were the matching references. A fresh Linux capture reproduced them exactly.
- Linux's PNG readback currently runs inside the video-recording path. `--capture-frame` also needs `-record_video`; otherwise the smoke can exit successfully without producing a PNG.

Diagnostic commit [`4f6aa018`](https://github.com/wbniv/WorldFoundry/commit/4f6aa018) logged each frame-20 batch's texture flag, handle, vertex colors, UVs, normals, and model-view matrix in both backends. Opaque texture-handle addresses were excluded from cross-process equality comparisons. For the affected batch, both handles were null:

RB batch=5 vertices=36 use_tex=0 handle=(nil) lighting=1

RB v -0.5 0.5 1 rgb 0.16796875 0.33203125 0.38671875 uv 0 0 n -0 0 1

Both batches explicitly disabled texturing. The difference already existed in CPU-generated material data, so texture binding, atlas UVs, parent texture handles, and the Metal white fallback were not the cause.

Batch 5 belongs to actor **#11, `matte_11`**, authored in [snowgoons.lev](../../wflevels/snowgoons-blender/snowgoons.lev) at `(3.071487427,3.636245728,1.370666504)`. Its model type is `MODEL_TYPE_BOX`: the mesh is generated by `RenderActor3DBox`, rather than loaded from a model asset. The affected −X face uses material index 1 and zero-based `cubeFaceList` triangles 6–7. Its projected corners are:

```text
(312.816,389.023)  (331.198,397.801)
(331.131,423.642)  (312.857,413.765)
```

These enclose the observed mismatch. The 108 different vertex records cover three procedural boxes, but only this lit face contributed different visible pixels.

## Why seeding alone does not fix it

The old code in [rendacto.cc](../../wfsource/source/renderassets/rendacto.cc) was:

```cpp
Color tempColor(rand()%230 + 26, rand()%230 + 26, rand()%230 + 26);
```

Two independent portability assumptions fail:

| Property | Linux reference | macOS |
|---|---|---|
| First three libc draws with seed 1 | `1804289383, 846930886, 1681692777` | `16807, 282475249, 1622650073` |
| Each draw modulo 230, plus 26 | `129, 72, 193` | `43, 85, 99` |
| Observed constructor argument evaluation order | GCC: blue, green, red | Apple Clang: red, green, blue |
| Resulting material RGB | `(193,72,129)` | `(43,85,99)` |

Both libc generators already start with the equivalent of seed 1. Explicitly calling `srand(1)` does not make their algorithms identical, and it does not specify which constructor argument receives which draw. The argument order above describes the tested builds, not a portable guarantee of either compiler.

[rendfcl.cc](../../wfsource/source/gfx/glpipeline/rendfcl.cc) divides the material channels by 256 before submission. With the matching shading inputs, those colors produce the observed pink and teal pixels. The problematic expression was already present in repository root commit `a2784f6e` (2010-05-01); the new Metal renderer exposed a longstanding shared-code portability defect.

## Fix and regression protection

Fix commit [`8bb1a162`](https://github.com/wbniv/WorldFoundry/commit/8bb1a162) replaces `MakeRandMaterialList` with `MakeBoxMaterialList`, using [BoxColorSequence](../../wfsource/source/renderassets/box_color.h):

- Specify the Linux seed-1 sequence directly: degree-31 additive feedback, separation 3, unsigned 32-bit wraparound, low bit discarded; Park–Miller initialization and 310 warm-up draws.
- Draw blue, green, and red in separate statements before constructing the color. This preserves the Linux reference's channel assignment.
- Keep this visual sequence separate from gameplay RNG state. Retain the original three libc draws per box so existing gameplay random sequences do not shift merely because of this fix.

The guarantee is a portable procedural-color sequence for the same box-construction order. It preserves the tested snowgoons reference and the old unperturbed Linux seed-1 sequence; it does not preserve arbitrary colors formerly affected by unrelated gameplay RNG calls. It also does not attempt to make gameplay's libc RNG portable.

Temporary actor/backend traces were removed. Neither backend's shader, texture handling, nor pixelmap code requires a production change.

[box_color_test.cc](../../tests/box_color_test.cc) checks the first four reference colors, a checksum over 10,000 RGB triples, and independence from libc reseeding. [compare_renderer_frames.py](../../tests/compare_renderer_frames.py) compares captures against a [frozen Linux PNG](../../tests/fixtures/renderer/snowgoons-linux-frame20.png). Both checks now run in `macos-desktop-debug`. The image gate allows at most three levels of error per channel, with no allowance for pixels exceeding that tolerance. Against the original Mac image, it fails on exactly the 455 face pixels, whose maximum channel difference is 148.
